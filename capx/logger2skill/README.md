# SkillOpt 实验流程与真机 weight_classify 接入说明

这份 README 供真机服务器上的 agent 接手实验。真机已经能完整执行 `weight_classify`，也已有人工整理好的真机技能库；接入时保留这些实现，只连接“本次执行结果 → SkillOpt 更新技能 → 下一次执行读取新技能”的循环。

本文记录截至 2026-11-15 的实验方法，并区分本机最新实验流程与已经上传的代码。本文的提交只新增文档，不启动实验、不安装机器人环境、不同步其他未提交的实现。

## 1. 实验究竟比较什么

每组使用同一份真机初始技能库、同一组按顺序执行的 **20 个 seed／场景编号**，但各自维护独立的后续版本。已有库经过人工整理，因此这里比较的是“从已有知识继续维护技能”的效果，不是从空库学习。

可以沿用以下组别；具体运行哪些组由实验负责人确定：

| 组别 | 每次执行结束后的处理 |
| --- | --- |
| 固定初始库 | 不更新，20 次始终读取相同内容 |
| 普通 CC | 用相同整理模型自行总结，不加入我们的方法规则 |
| Our CC | 按我们的现行维护规则整理 |
| SkillOpt | 使用固定版本 SkillOpt 的反思模板和原生补丁操作 |

所有组保留相同的执行模型、任务 prompt、触觉与动作 API、判分、代码生成预算和物理执行预算。各组可以因自身经验产生不同代码和日志。20 个真机场景需要记录物体、摆放与初始化约定；相同整数 seed 本身不能保证现实场景一致。

本说明主要交付 SkillOpt 的接入方法，不意味着另外三组已经在真机部署完成。

## 2. 每个 seed 的顺序

```text
读取本组 active 技能版本
    ↓
按当前任务投递技能 + 原任务 prompt + 当前视觉/公开 API
    ↓
执行模型生成一个完整 Python 程序
    ↓
真机运行，保存代码、公开日志、动作计数和任务最终结果
    ↓
SkillOpt 读取本次案例、实际 API 文档和当前完整技能库
    ↓
一次模型响应提出 Markdown 补丁
    ↓
宿主程序应用补丁并检查；通过则保存新版本，否则保留旧版本
    ↓
下一 seed 重新生成代码，并使用本组当前 active 技能
```

- 一次任务执行整理一次，不等待八项任务全部完成。单任务的 20 seed 就是 20 次执行，最多 20 次正常整理。
- 每个 seed 重新生成完整程序，不继承上一 seed 的完整程序或 Python 变量。
- episode 内不自动生成第二段代码，也不让 SkillOpt 接管当前机器人的恢复动作；程序内部仍可使用已有的循环和控制逻辑。
- 成功和失败案例都可用于整理。没有值得修改的内容时，空补丁合法。
- 更新不额外消耗一次真机验证。下一 seed 的实际结果反映使用新库后的表现，但不能单凭一次结果把变化归因于某条技能。
- 第 20 次执行后的整理可以保存，须标注“尚未被后续执行使用”。

## 3. 当前使用的是哪一部分 SkillOpt

上游来源：[microsoft/SkillOpt](https://github.com/microsoft/SkillOpt/tree/bc0a392ef0a7f92840ec673d80204d34ced169d0)，固定 commit 为：

```text
bc0a392ef0a7f92840ec673d80204d34ced169d0
```

当前适配复用：

- `skillopt.gradient.reflect`：轨迹文本格式化、反思模板加载、响应解析。
- `analyst_error` / `analyst_success`：按本次结果选用失败或成功分析指导；结果未知不能包装为成功案例。
- `skillopt.optimizer.skill.apply_patch_with_report()`：应用 `append`、`insert_after`、`replace`、`delete` 编辑。

最近实验使用 **`update_mode: patch`**。模型看到整个现有库，但只返回本轮需要的修改，宿主把修改应用到完整旧库。没有改到的原文保留；不能用“一条新技能”覆盖整库。适配层每次最多处理 4 个编辑操作，允许少于 4 个或零个。

技能的存储结果仍是 **Markdown `skill.md`**。响应里的 JSON 是上游补丁协议，不是要求把技能正文变成 JSON。例如一次只需追加内容时，响应可包含：

```json
{
  "batch_size": 1,
  "failure_summary": [],
  "patch": {
    "reasoning": "根据本次公开证据决定是否需要修改",
    "edits": []
  }
}
```

需要新增时，`edits` 中使用 `{"op":"append","content":"实际 Markdown 内容"}`；替换和删除使用旧文档中确实存在的 `target`。最终应沿用对应的上游模板，不另造 CC 的文件修改格式。

**实验应标为“SkillOpt 单次反思与补丁更新适配”。** 此处没有运行原版完整的多阶段聚合、候选选择、独立留出环境验证、接受门槛及元优化流程。没有训练检索选择器，也没有独立的内容审核模型调用。

Claude Code 在这个适配中只是模型调用通道：宿主把模板、技能和本次案例放进请求，使用 `claude -p` 得到响应。它不是采用 Our CC 的四阶段本地文件编辑流程。不要把 Our CC 的整份 `MAINTENANCE.md` 加到 SkillOpt 请求里，然后把结果当作原生 SkillOpt 基线。接口、标定保护和任务路由是机器人接入约束，需要在实验中如实说明。

## 4. 初始库、更新范围与下一轮投递

### 真机初始库

直接冻结用户已经整理好的 **真机 weight_classify 库**，保存完整内容及文件哈希。CC 和 SkillOpt 都从这一份内容开始，各自复制到独立实验目录。

SkillOpt 可以把多个 Markdown 文件机械合成 `skill.md`，保留原文、条目边界、标定条件与适用范围；不要先让模型重写初始库。CC 仍可保留原多文件格式。首次实际发送给执行模型的技能文本应核对一致，不能只有文件内容相同而首次投递不同。

本机历史仿真用过 `original-21-3758efb`。**真机不默认导入这 21 条，也不移植仿真的 0.2 px 分界、抓取坐标、夹爪参数或传感器量程。** 真机使用用户现有的标定及其测量条件。

### 允许更新什么

更新动作规划、探测与执行策略，例如怎样按已有协议取得有效读数、怎样组织已开放的动作调用。已确认的感知标定、单位、判定标准及适用条件保持冻结，不能凭一次成功重新拟合重量阈值，也不能修改任务判分或机器人 API。

当前仿真初始库的保护实现会冻结选定的感知条目全文。接入真机时需要明确哪些内容属于已有标定，并给各组相同的保护范围；不是把整个初始库都设成不可编辑。

### 谁看到什么技能

| 使用者 | 当前最新实验投递方式 |
| --- | --- |
| SkillOpt 整理模型 | 当前完整共享技能库 + 本次任务的一个案例 |
| 执行模型 | 按当前任务路由匹配到的技能条目全文 |

最新实验使用 `task_routes_v1`，保留条目的 `task_types`、`tasks`、`not_tasks` 等适用范围。更新条目时保持路由，新策略也必须有适用范围。执行侧不是仅投递 summary，也不是把八任务所有条目都塞给一个任务。

这一任务路由是我们的接入层，不是 SkillOpt 自动学出的检索。当前完整条目投递设 `memory_max_chars: null`，没有旧的 12,000 字符静默截断。必须保存每轮实际投递文本，才能核对修改是否真的进入下一轮输入。只有 weight_classify 的真机库也应保留其适用范围，不需要增加向量检索。

## 5. 每次交给整理器的案例

从本次真机执行中导出以下信息，不需要重新运行任务来补案例：

| 字段 | 内容及来源 |
| --- | --- |
| `case_id`、`task`、`seed` | 唯一运行标识、实际任务名和场景编号 |
| `task_prompt` | 当次真正发送的任务要求 |
| `code` | 当次真正执行的完整程序 |
| `stdout`、`stderr` | 本次程序的公开日志和异常；包括允许公开的触觉读数、动作与错误信息 |
| `api_documentation` | 当次执行模型看到的真实 API 文档，记录来源和哈希 |
| `execution_ok` | 程序执行是否正常结束，未知用 `null` |
| `final_success` | 由已有真机评估规则得到的最终任务结果，未知用 `null` |

API 文档不能省略，尤其是参数含义、默认值、坐标系和返回值。否则整理器可能把错误调用当作合法策略写入技能。

本机新版 `make_case()` 的 `api_documentation` 是包含 `status`、`source`、`text`、`sha256` 的对象。真机导出器可以保持这个结构；`sha256` 对实际文档文本计算，不填写占位校验值。

只传允许公开的触觉与执行信息。不把逐步真实重量、隐藏类别、评分内部状态或私有标签混入日志。**已结束 episode 的最终结果可以用于整理；它不等于允许执行中的代码读取答案。** 退出码为 0、程序打印成功、某个读数过阈值，都不能替代真机原有的最终判分。

本次执行的代码与公开日志是整理依据，旧经验已经在当前库中；不需要把全部历史原始运行日志再次拼入每个请求。

## 6. 调用预算、失败处理和版本保存

最近本机仿真配置的实际设置如下，仅用于说明已有实验；真机各组应在开始前统一冻结自己的预算。

| 配置 | 最近仿真值 |
| --- | --- |
| 执行模型 | `gpt-6.1-sol`，最多 8192 输出 token |
| 整理模型 | `claude-sonnet-4-6` |
| SkillOpt 每个整理尝试 | 一次模型响应、无工具调用、无独立审核 |
| 整理输出上限 | 64,000 token，是上限而非实际消耗 |
| 整理总时限 | `timeout_s: null`，没有旧的 300 秒总时限 |
| 整理无进展时限 | `idle_timeout_s: 900` |
| 更新模式 | `patch` |

单个整理尝试用 `max_calls=1`、`--max-turns 1` 和禁用工具实现。**这不等于整个实验绝不会多次请求**：最近仿真外层配置还允许整理超时后最多重试 3 次。若真机要求每个 seed 至多一次整理请求，应把外层 curator 重试设为 0；若允许重试，所有尝试的 token 和耗时都必须累计，不能只记最后成功的一次。

执行模型和整理模型调用都清除代理，不把凭据写进配置快照或 Git。调用前可在当前 shell 执行：

```bash
unset HTTP_PROXY HTTPS_PROXY ALL_PROXY http_proxy https_proxy all_proxy
```

更新过程由宿主完成：复制 active 库为候选 → 调用模型 → 应用补丁 → 检查格式、接口约束、标定保护及路由 → 保存版本并更新 active 指针。模型不负责执行 Git 或操作机器人。

- `adopted`：有修改且通过接入检查，下一 seed 使用它。
- `unchanged`：没有内容变化，继续旧版本。
- `rejected` / `failed`：补丁无法应用、检查失败或服务失败，保留旧版本并记录原因。

`adopted` 只代表更新可以被框架加载，不保证技能内容正确，更不等于已经提升任务成功率。我们这里没有额外的 LLM 内容审核或真机候选验证。

已生成代码之后的执行超时按任务失败计入实验，同时保留 `final_success: null`（若确实没有最终判分）和超时原因；不能把未知原生结果写成原生判负。代码生成之前的服务故障单独统计，不冒充任务能力失败。仿真自动 reset 重试也不能直接套到真机：是否可以重启一次执行由现有真机控制流程确认。

## 7. 真机 agent 要接的地方

不重新部署 Isaac Sim、OpenTacBench、TacEx，也不改真机的抓取、采样、标定和判分。只需要连接以下环节：

1. **初始化库**：冻结用户提供的真机库，建立本实验独立版本目录及 active 指针。
2. **投递**：生成代码前读取 active，按任务选择技能，并保存实际发送文本。
3. **案例导出**：执行结束后从现有结果生成上一节的单案例，附实际 API 文档。
4. **整理与应用**：调用 SkillOpt 适配器，在候选副本上应用原生补丁，失败保留旧库。
5. **20 次调度与统计**：下一场景读取新 active；按 seed 累计结果和两类模型费用。

仓库中的参考入口：

| 文件 | 可参考的职责 |
| --- | --- |
| [experiment.py](experiment.py) | 按执行逐次整理、保存版本和累计指标；`run_loop()` 有执行与整理回调 |
| [evidence.py](evidence.py) | 导出公开案例，区分程序结果与任务结果 |
| [curators.py](curators.py) | `curate_skillopt()` 构造反思请求、应用原生 patch |
| [claude.py](claude.py) | 无代理模型调用、限制响应次数、提取 token 用量 |
| [worker.py](worker.py) | 单次整理工作进程 |
| [storage.py](storage.py) | 库版本、候选、active 指针、技能投递 |

**现有 `run_experiment()` 和 `execute_episode()` 是仿真入口，不能直接当真机启动器。** `load_suite()` 也有仿真任务、环境路径及 GPU 检查。真机应围绕现有执行入口接上上述环节，或实现执行回调并适配配置检查；不要为了运行这份说明而调用仿真任务。

### 远端代码与最新实验的差异

本 README 编写时，远端 `exp/logger2skill-skillopt` 的已有代码基线为 `50d458c012361b55a701975f8b5097c4c20b2362`。它已有单案例循环、原生 patch、一次响应调用及版本存储，但仍有较早的默认行为。

| 部分 | 该远端基线 | 最新本机实验 / 真机接入需对齐 |
| --- | --- | --- |
| 初始库 | 默认空库 | 用户现有真机非空库及不可变快照 |
| SkillOpt 执行侧投递 | 整份 Markdown 按字符上限截断 | 按任务路由投递完整条目，保存实际文本 |
| 案例 | 较早的公开代码与日志格式 | 增加当轮 API 文档、异常中断结果 |
| 标定保护 | 请求中的限制说明 | 已有标定内容的宿主保护 |
| 预算与重试 | 旧 YAML 默认值 | 使用本实验明确冻结的配置，不复制旧默认值 |

最新本机的 `initial_library.py`、`routing.py`、`retries.py` 等辅助模块尚不在这个远端代码基线中。本次只上传 README，不把这些未提交代码一并发布。**因此本说明是接入规范，不是已经打包完成的真机运行脚本。** 另一个 agent 应先检查实际 checkout，补齐所需的轻量接入，再提交实现；不要声称仅拉取此分支就已经对齐最新实验。

尤其不要把本机 `initial_library_path` 直接指向任意真机文件夹并假定导入成功：本机导入器要求特定 manifest。真机端需导出相应快照，或在自身宿主中实现同等的内容冻结和哈希检查。

## 8. 需要保存与报告的产物

各组使用独立目录。以下是建议的真机产物布局，不要求改现有运行日志名称：

```text
real-weight-classify/<group>/<experiment_id>/
  experiment.json                 # 20 场景顺序、模型、预算、版本及初始库 hash
  initial_library/                 # 共同初始内容的只读副本
  library/active.json
  library/versions/<version>/
  episodes/<case_id>/
    delivered_memory.txt
    code.py
    case.json
    execution_result.json
    curation/                     # 请求、响应、token、补丁、差异、采用结果
    metrics.json
  metrics.json                    # 逐 seed 累计结果
```

至少统计：

| 指标 | 口径 |
| --- | --- |
| 成功数 / 20 | 使用现有真机任务成功判定；未知、超时和基础设施问题另列 |
| 成功曲线 | 第 k 次执行的结果及截至 k 的累计成功率，不只展示最后一次 |
| 成功 episode 平均动作步数 | 只对成功执行求均值；固定是高层动作调用还是控制步，不混用 |
| 代码生成 token 与耗时 | 单独累计；包括实际发生的服务重试 |
| 技能整理 token 与耗时 | 单独累计；包括未采用、失败及重试的尝试 |
| 总 token 与总耗时 | 代码生成、执行、整理各项可分别核对 |
| 库更新状态 | adopted / unchanged / rejected / failed，以及下一次实际使用版本 |

本机 `execute_steps` 指服务端动作请求数，不是物理仿真步；真机须记录自己的计数单位。Claude 的 input、output、cache read、cache creation 分开保存，不重复累加终端汇总与流式事件。缺失统计为未知，不能填 0；费用不能简单用总 token 乘一个统一单价。

## 9. 给真机服务器 agent 的交接要求

> 已有真机 weight_classify 能运行，也已有适用技能库。请保留现有执行与判分，仅按这份 README 接入 SkillOpt 的单案例反思和原生 Markdown patch 更新。每组从相同真机初始库独立开始，按同一 20 场景顺序运行，每次新生成一个程序，执行结束整理一次，下一次加载本组更新版本。保留已有标定，不把仿真的阈值或物体坐标接口迁入真机。先完成导出、投递、补丁与版本流转的离线接线验证；真实运行由实验负责人确认后启动。记录代码生成与技能整理各自的 token、耗时、结果及实际投递内容。

离线接线可以使用一份已有真实运行结果完成，不需要为检查格式再动机器人。验证应证明：非空初始内容确实进入请求、实际 API 文档进入整理、合法补丁被下一轮投递、非法补丁保留旧库、不同实验组不会互相覆盖。
