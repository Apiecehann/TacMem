# 触觉技能库维护规则

这份文档管两件事：**加一条新技能时要守什么**，和**这个库该多久检查一次、查什么**。

它不管内容本身（内容在 `skills/*/*.md`），也不重复格式的机械定义（在 `library.py`）。
它管的是那些**测试抓不到、但会让库慢慢烂掉**的判断。
**设计理念与框架住 `docs/univtac_tactile_skill_library.md`**（原来叫 `DESIGN.md`）——
这里的规则都是从那边推出来的。

---

## 三条前提

所有规则都是从这三句推出来的，冲突时回来看它们：

1. **库不是笔记，是 prompt 素材。** 库里每一条都会进某个任务的 prompt，
   所以每一条都得值它占的那一行。
2. **摘要就是投递的全部。** compact 渲染只发 `- <名字>: <摘要>`，
   正文永远不进 prompt。**正文里写的东西，LLM 看不到。**
3. **一条规则一个家。** 第二个地方需要它，就写指向正主的指针，不写副本。
   这个库存在的理由就是"同一句话在几个地方各写一遍然后漂移"。

---

## 一、加一条技能之前，先过三道闸

### 闸 1：它是一条技能吗？

| 你想写的东西 | 归属 |
|---|---|
| 这个函数做什么、参数取值范围与**取这个值的依据**、返回字段的含义与量纲、服务端行为、硬限制 | **API docstring**（`univtac_api.py`）|
| 这个任务要什么、成功判据是什么 | **任务 PROMPT** |
| 拿读数**怎么下判断**、先做什么后做什么、错了怎么退 | **技能库**（这里）|
| 这样试过，不行 | **不进库** —— 盘点文档 §4.5（`docs/univtac_tactile_skill_inventory.md`）|

⚠ **最容易判错的一条线：读数的含义 vs 读数的用法。** 2026-10-06 我就在这里判错过三处，
把 API 自己的性质当成"怎么用"挪进了技能库，被用户纠回来：

- `depth_mm` 的标尺（34 远平面 / 27-28 轻握 / 20 硬停）→ **是 `depth_mm` 的含义，属 API**；
  "取 min(左,右)、绝不取平均" → 读法 → 技能库（`depth-grip-scale`）。**两边都要有，不冲突。**
- `detect_slip` 的 `coherence_threshold` 为什么默认 0.7（再低分不开剪切和压缩）→ **是参数的依据，属 API**；
  "读任何标记量前先拿相干度 0.70 把关" → 指令 → 技能库（`confidence-gate`）。
- `close_gripper` 的 `position` 什么时候才起作用（物体够硬、手指别得住）→ **是参数的成立条件，属 API**；
  "按宽度选一个刚够着的握位" → 配方 → 技能库（`finger-position-grip`）。

判据一句话：**问"这在任务不存在时还成立吗"——成立⇒是 API 的性质⇒docstring。
再问"这是不是给我一个动作指令"——是⇒技能。** 一个数字可以合法地出现在两边，
只要两边说的是**不同的话**（含义 vs 指令）。

**⚠ 反方向也会错，而且更隐蔽：摘要整句只是"字段是什么意思"，没有指令。**
2026-10-06 复查全库 52 条时逮到 5 条（`contact-flag-not-proximity`、`shear-vs-displacement`、
`mirrored-shear-slide`、`slip-pair-baseline`、`servo-landing-error`）——它们的摘要都是
把 docstring 里已经写过的字段含义复述一遍，真正的指令躺在正文里（正文不进 prompt ⇒
LLM 只拿到了定义，拿不到该怎么做）。**改写方向：把正文里那条指令提到摘要，含义交回 docstring。**
自查一句话：**这条摘要，去掉它 LLM 会做错什么？** 答不上来（"它已经知道了"）就说明它只是在复述。

**⚠⚠ 还有一种：库里写的 API 行为已经过期。** `servo-landing-error` 原本讲"伺服落不准、
读回减掉误差再闭一次"——那是 2026-09-09 之前的落点行为；服务端给显式 `force_threshold`
的闭合改成伺服精确落点之后（实测 ±0.05 mm），那条技能描述的现象已不存在，只剩下误导。
它现名 `close-lands-on-target`，讲的是"读数对不上 ⇒ 是握歪了，不是要减掉的那个误差"。
**查 API 行为类技能时，光看它自洽不够，要去读服务端代码看它今天还成不成立**（§4.3）。

最后一行是硬规则，不是偏好：库里每条都会被投递进某个 prompt，而"别这么做"
**没有投递目标**。测试 `test_every_skill_reaches_some_task` 钉的就是这个。
已证伪的知识住 `docs/univtac_tactile_skill_inventory.md` §4.5，
那里每条都带"为什么不行"。**别把它们加进库**——那只会让路由代码为永不出门的内容
养一条特殊分支。

### 闸 2：库里已经有它的家了吗？

这就是 2026-10-06 一次合并掉 8 条的原因，也是加新技能时最容易重犯的错。
查三步：

1. 拿这条规则的**关键名词和数字**在 `skills/` 里搜一遍。数字最不会撒谎——
   `0.4 px`、`34.0`、`27.7` 这种一搜就知道有没有第二家。
2. 读候选技能的 `## How` 和 `## Traps`。规则常常已经躺在别人的陷阱条目里。
3. 看候选技能的 `copies:` 字段——它记着这条规则今天还抄在哪儿（见 §4.2②）。
   **prompt 和 docstring 里的副本已经清空**，所以这个字段现在指的都是文档，不再是"发出去的话"。

命中就**改那一条**，不要新建第二条。

### 闸 3：它投递给谁？

没有落点的技能就是死文件。两个路由键选一个：

- `task_types: [classify, insert, manipulate, screw]` —— **默认走这个**，
  四个类型覆盖全部 13 个任务。
- `task_types: []` + `tasks: [<任务名>]` —— **只有一种情况该这么写**：
  这条技能带**按物体标定的数字**，而同一类型里有别的任务不能拿到它。
  例子：方块是 `0.10/0.06` 分界 1.2 mm，罐是 `0.50/0.25` 分界 10 mm，
  两者同属 classify，只按类型走会让两边互相拿到对方的数字。

任务名必须与 `env_configs/univtac/*/low_level_*.yaml` 里的 `task_name` 一致。
写错加载期直接报错，不会静默路由到空。

## 二、怎么写

### 2.1 文件骨架

一个技能一个文件，`skills/<family>/<name>.md`，文件名**必须等于** `name`。
`family` 取 `sense` / `act` / `place` / `protocol` 之一。

```markdown
---
id: S1                    # 稳定短号，盘点文档靠它交叉引用
name: depth-grip-scale    # 必须等于文件名
family: sense
summary: 一行，就是投递出去的那一行
task_types: [classify, insert, manipulate, screw]
channels: [depth]         # 可选
objects: any              # 可选：这些数字是在什么物体上量的
evidence: 为什么信它，带 n 和实测区间   # 必填，测试钉住
copies: []                # 可选，见 §4.2②
---

## How
怎么做。

## Traps
这条规则最容易踩反的地方。
```

- **必填**：`id` / `name` / `family` / `summary` / `task_types`；`evidence` 非空
  （`test_every_skill_has_evidence_and_a_summary`）。
- **未知字段会报错**，不是忽略。
- `id` 一旦分配就不复用：合并掉一条，它的号跟着退休，别把号让给新技能
  （盘点文档里划掉的行还指着它）。

### 2.2 摘要——唯一有硬约束的地方

**一行，一条规则 + 它自己的判据数字，不写产生它的推理。**

- 长度：全库现在平均 **20.0** 词、最长 **58** 词（`lead-by-overshoot`——
  第二十二组起最长换了人，方向那条从 59 压到 55）、
  次长 55 词（`thread-direction-by-legs`，第二十二组让出四词换来
  "两条腿各读自己**改变了多少**"这条规则，见 §五末第二十二组），
  再往下 44 词（`wrist-limit-segmentation`，
  第二十组把终点半句从"接着拧到力矩到位"换成"坐底即停"）、
  41 词（`confidence-gate`，第二十一组）、30 词（`mirrored-shear-slide`，第二十二组）、
  28 词（`small-step-insertion`）；
  ★ 第十八组动了这两条的最长行，方向那条 **−3 词**：加进去的是一句正文早就写着、
  却没进投递块的话（**"一条腿一个方向""读数高的那条在拧紧"**——模型上一轮因此
  把两条腿都朝同一方向转，见 §五末第十八组），换掉的是同字数的"the thread's
  direction from two 30° legs"；同时把"no measurement""both legs read negative"
  两处压成同义的短说法（理由保留成半句，因为它正是"0 不是中性值"的根据）。
  导程那条 **+12 词**补的是**下界**——这一次缺的不是"说清哪个调用"，是"说少了"。
  **往 50 词以上写之前，先看有没有一句话是同一件事的第二次表述。**
  测试上限是均值每行 25 词、每类合计 800 词。往 20 词以上写
  之前先问自己是不是塞了两条规则——但**"说不清用哪个调用"也是规则的一部分**：
  38 词那条里有一半篇幅是在点名调用，因为两轮 eval 都死在这个空档上。
  `small-step-insertion` 长出来的那半句同理——**"不能用哪个动作"也是规则的一部分**，
  模型就是在那里把 2 mm 下限补成了死循环。
  `lead-by-overshoot` 多出来的"不是一次搜索"同理：第六轮 eval 里模型正是拿一次
  搜索把自己锁在比真值小一个数量级的导程上。
  44 词那条（第二十组之前是 41）是把"什么时候**停止**做某个动作"写在里面的规则：
  卷手腕的手续和它的终止条件是同一个判断（还该不该换手），拆成两行就等于
  把同一个判断放进两个家（§3.4），而模型上一轮正是靠一遍遍换手把刚建立起来的
  力矩放掉的。第十六组又给它长了三个词——那个动作的触发条件原本是一个**没有可观察量
  的词**（"坐底"）：模型能拿到的同义词只有 API 的 `reached`，而 `reached` 要求它别停，
  于是规则读起来像一句自相矛盾的话。接上一个读数，它才执行得了。
  **55 词那条（第十四组）是同一件事的第三次**：只写"不许"拦不住。禁止句
  （"a rejected one is missing, not zero, and must not enter a comparison"）当时就在
  投递块里，模型照样写了 `if sa is None: sa = 0.0`——于是这一行把**缺读数之后该做什么**
  和**为什么不许填 0**（半过喂下两条腿读的都是负数，填进去的 0 比它们都大）一并写了进去。
  往这一行再加内容之前先看第十四组：**能拦住的是动作和数字，不是语气。**
  ★ 第十八组把它压回 52 词，**理由那半句留着**：`since both legs read negative and
  a filled-in zero outvotes them` → `since a zero outvotes a real reading`（"两条腿都读负数"
  这半句移回正文——那是机制，正文里本来就有）。**"0 不是中性值"这个反直觉的判断
  需要它自己的半句理由**，删掉它就是拿一整轮 eval 去赌模型自己不会把 0 想成中性。
- ★ **2026-10-08 用户反馈：技能要写得简单、明确——前置条件太多就容易误导模型。**
  可操作的形式：**一行一件事，先给动作，再给一个数字；条件和例外写进正文，
  不要都堆在摘要里。** 需要"当 A 且 B 且 C 时才 D"的规则，先问这条限制
  是不是本该在 API 文档里（那就是"性质"，§二），或者是不是根本可以不写
  ——第十四组那 55 词和第十五组新长出来的 8 词都是**给一句话补范围**，
  不是加第二件事，写的时候仍要按这个标准审。
- 不写"因为……所以……"。理由、阈值来源、失效条件全部放 `evidence:` 或正文。
- 用命令式、英文，和库里其他行同一个语气。

⚠ **写完必须验，不能只看文件里有。** 拿
`TactileSkillLibrary.default_library().render_for_task("<任务名>")` 打出来，
确认那一行真的在投递块里。

这是本库最常踩的坑：把规则补进 `## How`。正文不进 prompt，补了等于没补。
2026-10-06 的 `z_approach=0.1` 就是这么补错的——写进了正文，
复核词数时才发现投递块一个字没变。

### 2.3 正文

`## How` 讲怎么做，`## Traps` 收最容易踩反的地方。**正文字数不影响 prompt 预算**，
所以宁可写全：理由、阈值来源、失效条件、反例都放这儿。

正文里引用另一条技能用 `[[技能名]]`。名字写错测试会报（`test_cross_references_resolve`）。

### 2.4 数字的纪律

每个阈值都要能回答两个问题：**在什么物体上量的**、**n 是多少**。写在 `evidence:` 里。

按物体标定的数字**互不通用**——这正是 `no-calibration-transfer` 那条技能自己在讲的事，
别在库里制造它的反例。把方块上量出来的分界值拿去罐上，读数不会报错，
它会返回一个大小合理的错答案，这是最坏的一种失败。

**并且：数字是在某个几何上量出来的（见 §4.3）。**

## 三、合掉或删掉一条技能

合并比新增危险，因为它会**静默改变别的任务的投递**。

### 3.1 合并前必查路由覆盖面

把两条技能各自覆盖的任务列出来（`for_task()`），确认幸存那条**覆盖得住**被删那条。

2026-10-06 差点出事：`depth-stop-seating` 覆盖插入+搬运共 8 个任务，
而它并进去的 `small-step-insertion` 只覆盖插入 3 个。照搬会让 5 个搬运任务
**静默**丢掉这条规则——不报错、不测试红，只是那些任务从此少拿到一条。
最后的处置是把幸存那条扩成 `[insert, manipulate]`：宁可多发一条，
也不让规则消失。

### 3.2 合并后必改指针

被删的名字在别处被 `[[...]]` 引用着。测试会报出来，但**报出来之后要人去改**，
改成指向幸存那条。

### 3.3 合并省的是"行"，不是"段"

投递只带摘要那一行，正文从来不进 prompt。所以**正文里各抄一遍的陷阱在预算上一分钱不花**，
它们花的是维护成本（改一处忘另一处）。算收益要按行算，不能按文件算。

反过来：如果合并的理由是"这两段正文很像"，那不是合并的理由，是**去重的理由**——
留一个正主，其余改成指针即可，条数不用变。

### 3.4 看着像重复、但不该合并的样子

判据不是"措辞像不像"，是"**它们是不是同一个判断**"：

- **特权分支**：同一件事，特权线走真值、非特权线走缓存 → 合了等于把那个特例
  发给全部任务（`bulb-grasp-pose` vs `grasp-pose-from-offset`）。
- **停的信号不同**：一个看垫子离开远平面，一个看被夹物体自己的高度 → 测量对象不同，
  不是措辞不同（`descent-until-contact` vs `descend-until-supported`）。
- **相邻但独立**：松手 vs 重抓（`keep-closed-if-task-allows` vs `preserve-existing-grasp`）。

**它抓格式和路由，抓不到内容。下面三节才是这份文档的重点。**

> 不能把那个方括号标记原样写出来，写了测试就红。

> 都会被原样投递给 LLM。**没有豁免名单可加**——测试文件和盘点文档能直呼其名，
> 只是因为它们在 `tests/` 和 `docs/`，压根不在扫描根里。

### 4.2 人看的检查

**① 重复是不是又长出来了。** 合并过一次不等于不会再长。跑这个扫描，0.22 以上的人看一眼：

```python
import re, itertools
from capx.tactile_skills import default_library

lib = default_library()
def sents(s):
    t = re.sub(r"```.*?```", " ", f"{s.summary}\n{s.evidence}\n{s.body}", flags=re.S)
    out = []
    for p in re.split(r"(?<=[.;:!?])\s+", t.replace("\n", " ")):
        p = re.sub(r"\[\[|\]\]|`|\*|_", "", p).strip()
        n = re.sub(r"\s+", " ", re.sub(r"[^a-z0-9 ]", "", p.lower()))
        if len(n) >= 45:
            out.append((n, p))
    return out
def sh(s, k=6):
    w = s.split()
    return {tuple(w[i:i+k]) for i in range(max(1, len(w)-k+1))}

seen = set()
for a, b in itertools.combinations(lib, 2):
    for sa, pa in sents(a):
        for sb, pb in sents(b):
            j = len(sh(sa) & sh(sb)) / len(sh(sa) | sh(sb))
            if j >= 0.22 and (a.name, b.name) not in seen:
                seen.add((a.name, b.name))
                print(f"{j:.2f}  {a.name} || {b.name}\n   A: {pa[:110]}\n   B: {pb[:110]}")
```

判据同上：**同一条规则**才合并；只是措辞像、判断不同就留着。

> 2026-10-06 实跑时它只报出 2 对，人工读全文另找出 5 处。
> **所以它是个辅助，不是清单。**

**② `copies:` 字段现在只剩文档，这是对的状态。** 2026-10-06 清过两轮：

### 4.3 触发式检查（发生了就必须做，不是"定期"）

**上游同步 / 仿真几何变了之后，库里相关的数字不是过期，是错的。**

有先例：上游把 `can_length` 从 0.120 改成 0.080、粗糙度改成真几何，
同一批阈值当场作废。数字是**在某个几何上量出来的**。

动作顺序：

1. 列出这次改了几何 / 材质 / 行程的物体；
2. 搜出库里有这些物体数字的技能（`objects:` 字段和摘要里的阈值）；
3. 重跑测量，更新 `evidence:` 里的 n 和实测区间；
4. 更新摘要里的阈值，**然后用 `render_for_task` 复核那一行真的变了**。

（`no-calibration-transfer` 讲的是跨物体不通用；这一条讲的是跨时间不通用。）

**任务改名或新增任务之后**：改 `taxonomy.yaml`，跑 §4.1 的测试。

### 4.4 没有的东西：内容回归网

**加一条技能会改 13 个任务的 prompt，而没有任何自动检查能告诉你分数变好还是变坏。**
一次 eval 要起服务端、按 seed 跑，成本高。

所以：**库的每次内容改动，在跑过 eval 之前都算未验证。**
别把"40 条测试全绿"读成"改对了"——它们只说明格式和路由没坏。
