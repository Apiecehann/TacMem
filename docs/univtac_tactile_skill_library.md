# 触觉技能库：设计理念与框架

**一句话**：把"这块凝胶读数意味着什么、据此该做什么动作"写成一条条独立的小规则，
按任务类型路由，作为 prompt 素材投递给 LLM。

它和 `capx/skills/`（从成功轨迹里抽 Python 函数）没有关系，这里存的是话，不是代码。

---

## 一、为什么要有它

在这之前，触觉知识同时住在四个地方：每个任务的 PROMPT、共用 API docstring、
`docs/univtac_api_reference.md`、ViTaForge 侧的 `SKILL.md`。四份副本各自演化，
结果就是**同一个阈值在 A 处是 0.10、在 B 处是 0.12，数字在一处而它成立的条件在另一处**。

这不是"整理"能解决的，因为四个地方的**读者不同**：

| 家 | 读者 | 它回答的问题 |
|---|---|---|
| API docstring | 拿到 10 个工具、13 个任务共用的 LLM | 这个函数是**什么** |
| 任务 PROMPT | 只做这一个任务的 LLM | 这个任务**要什么** |
| **技能库** | 按类型路由到的那个任务的 LLM | 拿读数**怎么下判断** |
| 盘点 / 维护文档 | 写判据的人 | 为什么是这样、试过什么不行 |

所以拆分的意义不止于去重：**docstring 一份要服务 13 个任务，它讲不清任何一个任务的具体做法；
PROMPT 一份只服务一个任务，它讲不清跨任务通用的读数纪律。** 技能库补的正是这两者之间的那一层——
"读数的用法"，它跨任务复用，但又按任务分叉。

---

## 二、边界：一条规则住哪儿

### 四个家，四类内容

| 内容 | 归属 |
|---|---|
| 函数做什么、参数范围与**取这个值的依据**、返回字段的含义与量纲、服务端行为、硬限制 | **API docstring** |
| 这个任务要什么、成功判据是什么 | **任务 PROMPT** |
| 拿读数**怎么下判断**、先做什么后做什么、错了怎么退 | **技能库** |
| 这样试过，不行 | **不进库**（盘点文档 §4.5） |

最后一行是硬规则：库里每条都会被投递进某个 prompt，而"别这么做"**没有投递目标**。
它属于写下一个判据的人，不属于执行任务的 LLM。

### 两个判据

1. **"这在任务不存在时还成立吗？"** 成立 ⇒ 是 API 自己的性质 ⇒ docstring。
   （参数取值依据、量纲、服务端行为、硬限制都属于这一类。）
2. **"这是不是给我一个动作指令？"** 是 ⇒ 技能库。

### 最容易判错的那条线：含义 vs 用法

一个数字可以**合法地出现在两边**，只要两边说的是不同的话：

- `depth_mm` 的标尺（34 远平面 / 27–28 轻握 / 20 硬停）是**读数的含义** ⇒ docstring；
  "取 min(左,右)、绝不取平均"是**读法** ⇒ 技能库。两条都要有，不冲突。
- `coherence_threshold` 默认 0.7 的**由来**（再低就分不开剪切和压缩）⇒ docstring；
  "读任何标记量前先拿相干度 0.70 把关"⇒ 技能库。

反方向更隐蔽：**摘要整句只是在复述字段含义，没有指令。** 那时 LLM 拿到了定义，拿不到怎么做。
自查一句话：**这条摘要，去掉它 LLM 会做错什么？** 答不上来就是在复述。

## 三、框架

### 3.1 一个技能 = 一个 markdown 文件

`skills/<family>/<name>.md`，`name` 必须等于文件名。四个 family：

`sense` 从凝胶里读出一个物理量 · `act` 让触觉信号启动/终止/修正动作 ·
`place` 把东西放下并确认 · `protocol` 跨前者的顺序与设计规则。

frontmatter 字段：

| 字段 | 作用 |
|---|---|
| `id` / `name` / `family` | 身份；id 一次分配不再复用（合并掉的那条号跟着退休） |
| `summary` | **投递出去的就是这一行**——一条规则 + 它自己的判据数字，不写推理 |
| `task_types` | 主路由键，四选若干 |
| `tasks` | 在类型之上再点名；**只有一种情况该用**：带按物体标定的数字，同类型里有任务不能拿到它 |
| `channels` / `objects` | 这条读的是哪个通道、数字在什么物体上量的 |
| `evidence` | 为什么信它，带 n 和实测区间 |
| `copies` | 这条规则今天还抄在哪儿（见 §四） |

正文 `## How` / `## Traps` 写全理由、阈值来源、失效条件、反例——
**正文字数不进 prompt 预算**，所以宁可写全。

### 3.2 投递：只发摘要

`render(compact=True)` 每条形如 `- <name>: <summary>`。
`render(compact=False)` 才带 `evidence` 和正文，那是给人看的。

两个后果，都是设计的一部分：

1. **往正文补规则等于没补**——LLM 看不到。补完必须拿 `render_for_task("<任务>")` 验一遍。
2. **合并省的是"行"不是"段"**——正文各抄一遍的陷阱在预算上一分钱不花，
   花的是维护成本。算收益要按行算。

### 3.3 路由：按类型全量

四个类型覆盖全部 13 个任务，类型语义就是"触觉在这个任务里扮演什么角色"：

- `classify` —— **触觉就是答案**：读数本身就是分类结果。
- `insert` —— **触觉是过程信号**：接触、倾斜、卡滞、坐底。
- `manipulate` —— **触觉出现在两端**：确认抓住了、确认被托住了。
- `screw` —— **触觉是唯一的裁判**：方向、导程、坐底，没有别的量可读。

默认**按类型全量投递**（一个类型拿到全库的 47–59%），不做按需精选——
因为精选需要判断"这个任务要不要这条"，而那个判断的准确率没有证据支持，
漏发一条的代价（LLM 少一条规则）比多发一条（多一行字）大得多。

`tasks:` 是给**按物体标定的数字**留的窄门：方块是 `0.10/0.06` 分界 1.2 mm，
罐是 `0.50/0.25` 分界 10 mm，两者同属 classify，只按类型走会让两边拿到对方的数字。

唯一的**按名投递**在灯泡的感知线上：`UniVTACBulbTighteningPerceptionCodeEnv`
（`capx/envs/tasks/tactile/univtac_bulb_tightening.py`）用 `tactile_skills = (...)`
点名交出 25 条里的 24 条——扣下 `bulb-grasp-pose`，因为那条配方走的是服务端的真值抓取
分支，而感知 API 把这个分支关掉了（理由与替代配方见该类的 docstring 和那份配置的文件头）。
**这是全仓唯一一处任务类覆盖投递**：
`test_the_only_hook_override_is_the_perception_bulb_variant` 同时钉住"只有这一个覆盖"
与"差的正好是那一条"两点，所以下一个想按名投递的人必须先改那条测试。

路由的钥匙是**任务名**，而任务名要从配置里取出来。这一步曾经是坏的：配置交给高层的是
低层 YAML 的**路径字符串**，代码却当成解析好的对象去读，名字于是解析成空串，**技能块一条
也没发出去**，而测试全绿（测试的桩自己捏了一个生产里不存在的形状）。修法是按"已建好的低层
环境 → 解析过的 cfg → 现读 YAML" 依次取，并用 34 个真配置各走一遍钉住。
**教训写进设计原则：路由的测试必须从真配置来。**

### 3.4 四件套的分工

| 文件 | 管什么 |
|---|---|
| `taxonomy.yaml` | 任务名 → 类型的表；测试拿它和 `env_configs/` 对账 |
| `library.py` | 加载、校验、路由、渲染；格式的机械定义 |
| **`DESIGN.md`**（本文） | 为什么这么设计、边界在哪 |
| `MAINTENANCE.md` / [历史原文归档](tactile_skill_maintenance_history.md) | 加/合/删一条时要过什么闸、多久检查一次、基线数字 |

## 四、设计原则

1. **一条规则一个家。** 第二个地方需要它，就写指针，不写副本。这个库存在的全部理由就是这条。
2. **库不是笔记，是 prompt 素材。** 每一条都会进某个任务的 prompt，所以每条都得值它占的那一行。
3. **摘要就是投递的全部。** 判定一条内容该不该进摘要，只看"LLM 少了它会不会做错"。
4. **投递量是成本，条数是维护成本，两者分开算。** 去重按条数算收益，砍投递按行数算。
5. **库里只放能下判断的东西。** 只讲了一个现象、没讲据此做什么的，是知识不是技能。
6. **数字必须带来源和适用范围。** 每个阈值都要能回答"在什么物体上量的、n 是多少"，
   因为按物体标定的数字互不通用，而混用的失败方式是不报错、返回一个合理的错答案。
7. **已证伪的知识不进库。** 它没有投递目标，进来只会让路由代码为永不出门的内容养特殊分支。
8. **没有内容回归网。** 加一条技能会改 16 个任务的 prompt，而没有任何自动检查能告诉你分数变好还是变坏。
   **跑过 eval 之前，内容改动一律算未验证。**
9. **路由的测试必须从真配置来。** 自己捏一个"配置长什么样"的桩，测的是那个想象，不是生产——
   名字解析失效就是这么躲过 39 条测试的（§3.3 末尾）。凡是"这段代码在生产里拿到的输入是什么"，
   就照生产的样子构造，或者干脆走一遍真配置。
